# ロード命令実行ユニット LoadUnit

## 機能説明

ロード命令パイプラインは、ロードディスパッチキューからロード命令を受け取ります。パイプラインでの処理後、結果はLoadQueueとROBに書き戻され、命令のコミットと、この命令に依存する後続命令のウェイクアップに使用されます。一方、LoadUnitはディスパッチキューとLoad/StoreQueueに必要なフィードバックを提供します。LoadUnitは128ビットのデータ幅をサポートします。

### 機能1：LoadUnitパイプラインステージの機能

* ステージ0

    * 異なるソースからのリクエストを受け取り、アービトレーションを実行します。

    * アービトレーションされた命令は、TLBとD-cacheにクエリリクエストを送信します。

    * パイプラインはステージ1にフローします。

  アービトレーションの優先度は、高いものから低いものへと以下の表にリストされています。

  Table: LoadUnitリクエスト優先度

  | ステージ0リクエストソース                               | 優先度 |
  | ------------------------------------------------------- | -------- |
  | MisalignBufferからのロードリクエスト                    | 高       |
  | dcacheミスによるloadQueueReplayのための再送             |          |
  | LoadUnitの高速リプレイ                                  |          |
  | アンキャッシュ可能なリクエスト                          |          |
  | 非キャッシュ可能なリクエスト                            |          |
  | LoadQueueReplayからのその他のリプレイ                   |          |
  | 高信頼性ハードウェアプリフェッチリクエスト              |          |
  | ベクトルロードリクエスト                                |          |
  | スカラロード/ソフトウェアプリフェッチリクエスト         |          |
  | ロードポイントチェイシングリクエスト                    |          |
  | 低信頼性ハードウェアプリフェッチリクエスト              | 低       |

  現在の昆明湖アーキテクチャは、ロードポイントチェイシングをサポートしていません。

* ステージ1

    * ステージ0からリクエストを受け取ります。

    * s1_kill：s1_kill信号は、高速リプレイの仮想物理アドレスマッチングが失敗した場合、L2Lフォワーディングが失敗した場合、またはリダイレクト信号がアクティブな場合にtrueに設定されます。

    * TLBまたはD-cacheにキル信号を発行する場合があります。

    * TLBから応答を受信すると、物理アドレスに基づいてDCacheをクエリします。ヒントケースの場合は、同時にDCacheに送信します。

    * st-ldフォワーディングのためにstorequeue && sbufferをクエリします。

    * ストアユニットのリクエストを受け取り、st-ld違反をチェックします。

    * 例外が発生したかどうかを確認します。

    * NC命令の場合、PBMTチェックを実行します。

    * prf_i命令の場合、フロントエンドにリクエストを送信します。

* ステージ2

    * ステージ1からリクエストを受け取ります。

    * PMPチェック応答を受信して、例外が発生したかどうかを判断します。同時に、例外のソースを統合します。

    * dcacheからの応答を受信して、再送が必要かどうかを判断します。

    * ld-ldまたはst-ld違反についてLoadQueueとStoreQueueをクエリします。

    * バックエンドに高速ウェイクアップ信号を送信します。

    * 再送の理由を統合します。

    * 非キャッシュ可能（nc）命令の場合、PMAおよびPMPチェックを実行します。

* ステージ3

    * ステージ2からリクエストを受け取ります。

    * SMSプリフェッチャーとL1プリフェッチャーにプリフェッチリクエストを送信します。

    * dcacheから返されたデータまたは転送されたデータを受信し、連結と選択を実行します。

    * アンキャッシュロードリクエストの書き戻しを受信します。

    * 完了したロードリクエストをバックエンドに書き戻します。

    * LoadQueue内のロード命令の実行ステータスを更新します。

    * バックエンドにリダイレクト要求を送信します。

### 機能2：ベクトルロード命令のサポート

* LoadUnitは、スカラと同様に、スカラよりも優先度の低い非整列ロード命令を処理します。具体的には：

    * ステージ0：

        * vlSplitからの実行リクエストを受け入れます。これはスカラリクエストよりも優先度が高く、仮想アドレス計算を必要としません。

    * ステージ1：

        * vecVaddrOffsetとvecTriggerMaskを計算します。

    * ステージ3：

        * バックエンドにfeedback_slow応答を送信する必要はありません。

        * ベクトルロードはライトバックを開始し、vecldoutを介してバックエンドに送信します。

### 機能3：MMIOロード命令のサポート

* MMIOロード命令は、それに依存するコンシューマ命令をウェイクアップすることのみを目的としています。

    * MMIOロード命令は、s0でバックエンドにウェイクアップ要求を送信します。

    * MMIOロードは、ステージs3でデータを書き戻します。

### 機能4：非キャッシュ可能ロード命令のサポート

* LoadUnitでの非整列ロード命令の処理プロセスは、スカラリクエストと同様ですが、スカラリクエストよりも優先度が高くなります。具体的には、非キャッシュ可能ロード命令はパイプラインを2回使用します。

    * 最初のパイプラインステージ：命令のNC属性を決定します。

    * 2番目のパイプラインステージ：

        * ステージ0：NC命令を識別し、TLB変換は不要です。

        * ステージ1：StoreQueueに転送要求を送信します。

        * ステージ2：ストアデータ転送条件を決定します（データが準備できていない - リプレイ処理、仮想物理アドレスの不一致 - リダイレクトN処理）。RAR/RAW違反要求を送信します。

        * ステージ3：違反シナリオを決定します（ldld vio-リダイレクト、stld vio-リダイレクト処理）。RARまたはRAWが満杯/準備ができていない場合、LoadQueueUncacheからの再送が必要です。再送が不要な場合は、ldoutを介して書き戻します。

* 非整列の非キャッシュ可能ロード命令はサポートされていません。

* LoadQueueUncacheからの転送データの取得をサポートします。

### 機能5：ミスアラインロード命令のサポート

* 非整列ロード命令は、パイプラインを4回使用します。

    * 最初のパイプラインステージ：ミスアライン命令かどうかを判断します。もしそうなら、LoadMisalignedBufferはミスアライン要求を送信します。

    * パイプラインが2回目に使用されるとき、分割からの最初の整列ロード命令が実行されます。実行が成功すると、応答がLoadMisalignBufferに送信されます。それ以外の場合は、LoadMisalignBufferから再送されます。

    * パイプラインの3回目で、2番目の分割整列ロード命令を実行します。実行が成功すると、応答がLoadMisalignBufferに送信されます。それ以外の場合は、LoadMisalignBufferから再送されます。

    * 4番目のパイプラインステージは、s0でロード命令に続くコンシューマをウェイクアップし、ロード命令はLoadMisalignBufferから書き戻します。

* Loadでの非整列ストア命令の処理プロセスは、スカラ操作のそれと似ていますが、以下の詳細があります。

    * ステージ0：

        * LoadMisalignBufferからのリクエストを、ベクトルおよびスカラリクエストよりも高い優先度で、仮想アドレスを計算する必要なく受け入れます。

    * ステージ3：

        * リクエストがLoadMisalignBufferからではなく、16バイト境界を越えない非整列リクエストである場合、LoadMisalignBufferによって処理される必要があります。キューリクエストは、io_misalign_bufインターフェイスを介してLoadMisalignBufferに送信されます。

        * リクエストがLoadMisalignBufferからであり、16バイト境界を越えない場合、リプレイまたはライトバック応答をLoadMisalignBufferに送信する必要があります。応答は、io_misalign_ldoutインターフェイスを介して送信されます。

        * misalignNeedWakeUp == trueの場合、直接書き戻します。それ以外の場合は、再送のためにLoadMisalignBufferに進みます。

### 機能6：プリフェッチリクエストのサポート

*   LoadUnitは2種類のプリフェッチリクエストを受け付けます。

    *   高信頼度プリフェッチ（confidence > 0）

    *   低信頼度プリフェッチ（confidence == 0）

*   プリフェッチトレーニングをサポートします。

    *   ステージs2：

        *   `io_prefetch_train_l1` を介してL1プリフェッチャを学習させます。

        *   `io_prefetch_train` を介してSMSプリフェッチャを学習させます。

## インタフェースタイミング

### LoadUnitインタフェースタイミング例

![LoadUnitインタフェースタイミング](./figure/LSU-LoadUnit-Timing.svg){#fig:LSU-LoadUnit-timing}

ロード命令がLoadUnitに入った後、ステージ0でTLBとDCacheにリクエストを出し、ステージ1でTLBからpaddrを受け取ります。ステージ2でDCacheヒット可否を取得し、同時にRAWおよびRAR違反をチェックします。ステージ3で`io_lsq_ldin` を通じてLoadQueueを更新し、`ldout` で書き戻します。

### ステージ0異なるソースのアービトレーションタイミング例

![ステージ0異なるソースのアービトレーションタイミング](./figure/LSU-LoadUnit-s0-arb.svg){#fig:LSU-LoadUnit-s0-arb}

図の例では、ステージ0で異なるソースのロード命令がどのように仲裁されるかを示しています。3番目のクロックでは `io_ldin_valid` のみが有効でハンドシェイクが成立し、次のサイクルでステージ1に進みます。5番目のクロックでは `io_ldin_valid` と `io_replay_valid` が同時に有効になり、リプレイの優先度がスカラロードより高いため、リプレイ要求が仲裁を獲得してステージ1に進みます。
