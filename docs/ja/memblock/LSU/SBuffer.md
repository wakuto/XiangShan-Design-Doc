# Storeコミットバッファ SBuffer

## 機能説明

sbufferの各エントリはキャッシュラインであり、各キャッシュラインは64バイト（4 vwords、各vwordは16バイト）です。

各バイトは、現在データが含まれているかどうかを示すために1ビットのマスクで示されます。

メタ情報には、ptag、vtag、state、cohCount、missqReplayCountが含まれ、具体的な機能は次のとおりです。

* ptag：物理アドレスタグ、物理アドレスのキャッシュラインオフセット以外の残りの部分。

* vtag：仮想アドレスタグ、仮想アドレスのキャッシュラインオフセット以外の残りの部分。

* state：状態、エントリの現在の状態を示します。
    * state_valid：エントリが有効かどうかを示します。
    * state_inflight：エントリがdcacheに書き込み要求を送信したが、まだ応答を受信していないか、dcacheがミスで応答したことを示します。
    * w_timeout：dcacheに送信された要求がミスし、再送を待機しています。
    * w_sameblock_inflight：このエントリと同じキャッシュブロックアドレスを持つ他のエントリがあります。他のエントリはすでにinflightであり、現在のエントリは割り当てられたばかりで、他のエントリがdcacheの書き戻しを完了するのを待つ必要があります。

* cohCount：0から1Mまでインクリメントし、エントリをdcacheに書き込むカウンター。

* missqReplayCount：以前にdcacheに送信された要求がミスになった場合に0から16までインクリメントするカウンター。その後、エントリはdcacheに再送されます。

### 特性1：sbufferのエンキューロジック

* 各サイクルでStoreQueueから最大2つの要求を処理できます。次に、要求が新しいエントリの割り当てを必要とするかどうかを確認します。両方が新しいエントリを必要とする場合、奇数偶数割り当てに基づいて2つの空きエントリが選択されます。2つの要求が同じptagを共有する場合、それらは同じ空きエントリに割り当てられます。

* 同じキャッシュラインを持つエントリがすでに存在する場合、新しいエントリを割り当てる必要はありません。データは既存のエントリにマージできます。ただし、同じキャッシュラインがすでにdcacheに送信されている場合（state_inflightがtrue）、マージは許可されず、新しいエントリを割り当てる必要があります。新しいエントリは、inflightエントリへの依存関係も記録する必要があります（w_sameblock_inflightをtrueに設定し、waitInflightMaskをinflightエントリのIDに設定することにより）。この依存関係により、新しいエントリは、inflightエントリが処理された後にのみdcacheに書き込むことができ、ストアの順序が維持されます。

* このエントリの状態ビットをvalidに設定します。

* 要求がマージのためにsbufferに入るとき、このエントリがたまたまdcacheへの書き込み用に選択された場合、マージが完了するまでdcacheの書き込みをブロックしてから、書き込みを続行する必要があります。

### 特性2：sbufferのデキューロジック

* sbuffer内のエントリは、受動的条件と能動的条件の両方でdcacheに書き込まれます。
    * 受動的：sbuffer内のエントリ数がしきい値に達し、置換が必要になります。
    * 能動的：atomicsUnitおよびfenceUnitからのsbufferをフラッシュする信号、またはマージ中またはロードへの転送中にタグの不一致が発生した場合、または以前にミスした要求が再送された場合。

* sbufferからの退出には2サイクルかかります。最初のサイクルでdcacheに書き込むエントリを選択してラッチし、2番目のサイクルでdcacheに書き込み要求を送信します。

### 特性3：sbufferデータの書き込み

要求がsbufferに到着すると、新しいエントリを割り当てるか、既存のエントリにマージします。データとマスクの書き込みは2サイクルで行われます。最初のサイクルで要求をラッチし、2番目のサイクルで要求のマスク（sb、sh、sw、sd）に基づいてデータを書き込み、対応するマスク（キャッシュライン内の特定のバイトが有効かどうかを示す信号）を設定します。

例：要求S0がsbufferに到着すると、S0は判断ロジックを実行し、要求が既存のエントリ（2番目のエントリ）にマージできると判断します。16'b0000000000000100のワンホット書き込みエンコーディングが生成されます。この書き込みエンコーディングを使用して、2番目のエントリの書き込み信号が生成され、S1にラッチされ、S0からの書き込みアドレス（例：キャッシュブロックオフセット0）、マスク（例：sw、4バイト書き込み）、およびデータがS1にラッチされます。S1は、S0からラッチされた情報を使用して、2番目のエントリの0番目のワードの下位4バイトの書き込み信号をアサートし、対応するデータを書き込み、0番目のワードの下位4バイトのマスク書き込み信号をアサートしてtrueに設定します。

### 特性4：sbufferの転送ロジック

* ロード操作は、それより前のストアからのデータを見つける必要があります。これは、ストアキュー、sbuffer、またはすでにキャッシュに書き込まれている可能性があります。

* sbufferで検索する場合、既存のエントリのタグを比較します。一致するエントリが見つかる場合があります。これは、まだdcacheに要求を送信していないものか、すでにdcacheに要求を送信しているもののいずれかです。まだ送信していないものが最新であるため、まだ送信していないものの優先度が高く、一致したデータをロードに転送します。

下図に示すように、転送クエリ要求はsbufferの0番目と15番目のエントリと同時に一致しましたが、0番目のエントリのデータが最新で、15番目のエントリは古いため、転送結果では0番目のエントリの優先度が15番目のエントリよりも高くなります。

## インターフェースタイミング

### ストア命令書き込みタイミングの例

io_in_*_validとio_in_*_readyがハンドシェイクすると、sbufferはstoreQueueの書き込み要求を受信し、アドレスを使用してチェックを行い、新しいエントリを割り当てるか、既存のエントリにマージします。io_in_*_bitsの情報を使用して項目を更新します。

![ストア命令書き込みタイミング](./figure/sbuffer-stin.svg)

### dcacheへの書き込みタイミングの例

io_dcache_req_readyとio_dcache_req_validがハンドシェイクすると、io_dcache_req_bits_*をdcacheに渡し、要求を転送してdcacheに処理させます。

![dcacheへの書き込みタイミング](./figure/sbuffer-en-dcache-timing.svg)

### 転送要求タイミングの例

転送要求にはready信号は必要ありません。io_forward_* _validが高くなると、この要求を処理する必要があります。要求のpaddrとvarddrを使用してクエリを実行します。データおよびその他の情報は、io_forward_*_validが高くなった次のサイクルで有効になります。

![転送要求タイミング](./figure/sbuffer-fwdtiming.svg)
