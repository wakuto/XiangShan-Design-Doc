# 読了後読込違反チェック LoadQueueRAR

## 機能説明

マルチコア環境では、ロード間の違反が発生する可能性があります。シングルコア環境では、同じアドレスへのロードの順序が乱れても通常は問題になりません。しかし、2つのロードの間に別のコアが同じアドレスにストアを行い、元のコアの2つのロードが順序を乱してスケジュールされた場合、新しいロードがストアによる更新結果を見逃し、古いロードは見てしまうという順序エラーが発生する可能性があります。

マルチコア環境におけるロード間の違反には、現在のDCacheがL2キャッシュからプローブ要求を必ず受信するという特徴があります。これにより、DCacheはこのデータコピーを積極的に解放します。このとき、DCacheはロードキューに通知し、同じアドレスでメモリアクセスを完了したロードキュー内のエントリに解放フラグを立てます。その後パイプラインに送られるロード命令は、ロードキュー内で自分より後にある同じアドレスのロード命令を照会します。解放フラグが見つかった場合、ロード間の違反が発生します。

LoadQueueRARは、完了したロード命令の情報を格納し、ロード間の違反を検出するために使用されます。ロード命令がロードパイプラインのs2ステージにあるとき、空きエントリを照会して割り当て、情報をLQRARに保存します。s3ステージで、ロード間の違反チェック結果が得られます。違反が発生した場合、パイプラインはフラッシュされ、リダイレクト要求がRedirectGeneratorユニットに送信され、違反したロード以降のすべての命令が破棄されます。

LoadQueueRARには、以下の情報をマークする必要があります。

* Allocated：エントリが有効かどうかを示します。
* Uop：MicroOp関連情報。
* Paddr：LoadQueueRARに入る命令の物理アドレスを圧縮したもので、合計16ビットです。
* Released：命令によってアクセスされたキャッシュラインが解放されたかどうかを示します。マルチコア環境では、L1キャッシュはL2キャッシュからプローブ要求を受信します。命令が非キャッシュ可能（nc）である場合、エントリ時に解放済みとしてマークされることに注意してください。

### 特性1：要求のエンキュー

クエリがロードパイプラインのステージs2に到達すると、エンキュー条件が満たされているかどうかを判断します。現在のロード命令の前に未完了のロード命令があり、現在の命令がフラッシュされていない場合、現在のロードはエンキューできます。

フリーリストから割り当て可能なエントリとそのインデックスを取得します。

エンキューされた情報はPaddrModuleに保存されます。これには、クエリの圧縮された物理アドレス（16ビット）と割り当てられたエントリのインデックスが含まれます。


### 特性2：ロード間の違反チェック

ロードがパイプラインのステージs2に到達すると、RARキューに現在のロード命令と同じ物理アドレスを持つより新しいロード命令があるかどうかをチェックします。これらのロードがすでにデータを取得しており、解放済みとしてマークされている場合、ロード間の違反が発生したことを示します。違反したロード以降のすべての命令をフラッシュする必要があります。

これは2つのサイクルに分かれています。

* 最初のサイクルでは、条件照合を行ってマスクを生成します。
* 2番目のサイクルでは、違反が発生したかどうかを示す応答信号を生成します。

### 特性3：解放条件

LoadQueueRAR内のロード命令が解放済みとしてマークされるシナリオは4つあります。

* missQueueモジュールのreplace_req信号は、mainpipeパイプラインのs3ステージでdcacheブロックの解放を開始します。解放信号は次のサイクルでloadQueueに入ります。
* probeQueueモジュールのprobe_req信号は、mainpipeパイプラインのs3ステージでdcacheブロックの解放を開始します。解放信号は次のサイクルでloadQueueに入ります。
* atomicsUnitモジュールからの要求がmainpipeパイプラインのs3ステージでミスした場合、dcacheブロックを解放する必要があります。解放信号は次のサイクルでloadQueueに入ります。
* エンキュー要求が非キャッシュ可能（nc）である場合、エンキュー時に解放済みとしてマークされます。

## インターフェースタイミング

### LoadQueueRAR要求エンキュータイミングの例

![LoadQueueRAR要求エンキュータイミング](./figure/LoadQueueRAR-enqueue.svg){#fig:LoadQueueRAR-enqueue width=70%}

io_query_*_req_validとio_query_*_req_readyの両方がハイの場合、ハンドシェイクが成功したことを示します。needEnqueueとio_canAllocate_*の両方がハイの場合、io_doAllocate_*がハイに設定され、クエリをエンキューする必要があり、FreeListが割り当て可能であることを示します。io_allocateSlot_*は、クエリをエンキューするエントリを受け取り、エントリに書き込む情報はio_w*です。

### ロード間の違反チェックタイミングの例

![ロード間の違反チェックタイミング](./figure/LoadQueueRAR-load-to-load.svg){#fig:RAR-load-to-load width=70%}

io_query_* _req_validとio_query_* _req_readyの両方がハイの場合、ハンドシェイクが成功したことを示し、LoadQueueRARはld-ld違反クエリ要求を受信します。現在のサイクルでマスク結果を取得し、次のサイクルでio_query_*_resp_validをハイに設定して応答を出します。

図の3サイクル目で最初の違反クエリ要求を受信し、4サイクル目で違反クエリ要求の応答を取得します。要求の情報はio_query_* _req_bits_で、応答の情報はio_query_* _resp_bits_です。io_query_* _resp_validとio_query_* _resp_bits_rep_frm_fetchの両方がハイの場合、ld-ld違反が発生したことを示し、現在の違反ロード以降のすべての命令をフラッシュします。
