# セカンダリモジュール L2 TLB

L2 TLBWrapper は以下のモジュールを指します。

* L2TLBWrapper ptw、L2TLBWrapper は L2 TLB のために抽象化レイヤーを提供します。

L2 TLB は以下を指します。

* L2TLB ptw

## 設計仕様

このセクションでは、L2 TLB モジュールの全体的な設計仕様について説明します。L2 TLB モジュールに含まれるサブモジュールの設計仕様については、このドキュメントの第3レベルモジュールの部分を参照してください。

1. L1 TLB からの PTW リクエストの受信をサポート
2. L1 TLB への PTW 応答の返却をサポート
3. 信号とレジスタの複製をサポート
4. 例外処理メカニズムをサポート
5. TLB 圧縮をサポート
6. 2段階アドレス変換をサポート

## 機能

L2 TLB は、ITLB と DTLB によって共有されるより大きなページテーブルキャッシュです。L1 TLB でミスが発生すると、L2 TLB にページテーブルウォークリクエストが送信されます。L2 TLB は、ページキャッシュ（セクション 5.3.7 参照）、ページテーブルウォーカー（セクション 5.3.8 参照）、最終レベルページテーブルウォーカー（セクション 5.3.9 参照）、ハイパーバイザページテーブルウォーカー（セクション 5.3.10 参照）、ミスキュー（セクション 5.3.11 参照）、およびプリフェッチャ（セクション 5.3.12 参照）の5つの部分に分かれています。

L1 TLB からのリクエストは、まずページキャッシュにアクセスします。2段階アドレス変換ではないリクエストの場合、リーフノードにヒットすると直接 L1 TLB に返されます。そうでない場合は、ページキャッシュでヒットしたページテーブルのレベルと、ページテーブルウォーカーおよび最終レベルページテーブルウォーカーの空き状況に応じて、ページテーブルウォーカー、最終レベルページテーブルウォーカー、またはミスキューに入ります（セクション 5.3.7 参照）。一方、2段階アドレス変換リクエストの場合、リクエストが onlyStage1 であれば、非2段階アドレス変換リクエストと同様に処理されます。リクエストが onlyStage2 で、リーフページテーブルにヒットした場合は直接返され、ヒットしなかった場合はページテーブルウォーカーに送信されて変換されます。リクエストが allStage の場合、ページキャッシュは一度に1つのページテーブルしかクエリできないため、まず第1段階のページテーブルをクエリします。2つのケースがあります。第1段階のページテーブルがヒットした場合、ページテーブルウォーカーに送信され、その後の変換プロセスが実行されます。第1段階のページテーブルがリーフノードにヒットしなかった場合、ヒットしたページテーブルのレベルと、ページテーブルウォーカーおよび最終レベルページテーブルウォーカーの空き状況に応じて、ページテーブルウォーカー、最終レベルページテーブルウォーカー、またはミスキューに入ります。ページテーブルへのアクセスを高速化するために、ページキャッシュは3レベルのページテーブルをすべて個別にキャッシュしており、同時に3レベルのページテーブルをクエリできます（セクション 5.3.7 参照）。ページキャッシュは ECC チェックをサポートしており、ECC チェックでエラーが発生した場合は、このエントリをフラッシュして再度ページウォークを実行します。

ページテーブルウォーカーは、ページキャッシュからのリクエストを受け取り、ハードウェアページテーブルウォークを実行します。2段階アドレス変換ではないリクエストの場合、ページテーブルウォーカーは最初の2レベル（1GB および 2MB）のページテーブルのみにアクセスし、4KB ページテーブルにはアクセスしません。4KB ページテーブルへのアクセスは、最終レベルページテーブルウォーカーが担当します。ページテーブルウォーカーがリーフノード（大ページ）にアクセスした場合、L1 TLB に返されます。そうでない場合は、最終レベルページテーブルウォーカーに返す必要があり、最終レベルページテーブルウォーカーが最終レベルのページテーブルにアクセスします。ページテーブルウォーカーは同時に1つのリクエストしか処理できず、最初の2レベルのページテーブルを並行してアクセスすることはできません。2段階アドレス変換リクエストの場合、最初のケースとして、allStage リクエストで第1段階の変換ページテーブルがヒットした場合、PTW は第2段階のリクエストをページキャッシュに送信してクエリします。ヒットしなかった場合、ハイパーバイザページテーブルウォーカーに送信され、第2段階の変換結果が PTW に返されます。2番目のケースとして、allStage リクエストで第1段階の変換リーフノードがヒットしなかった場合、PTW の変換プロセスは非仮想化リクエストの変換と似ていますが、PTW の変換プロセスで出現する物理アドレスがゲスト物理アドレスである点が異なります。これは、メモリにアクセスする前に第2段階のアドレス変換を行う必要があります。詳細については、ページテーブルウォーカーのモジュール紹介を参照してください。3番目のケースとして、onlyStage2 リクエストの場合、PTW は外部に第2段階の変換リクエストを送信し、resp を受信した後、L1TLB に返します。4番目のリクエストは onlyStage1 リクエストであり、このリクエストの PTW 内部での処理プロセスは非仮想化リクエストの処理プロセスと一致します。

ミスキューは、ページキャッシュと最終レベルページテーブルウォーカーからのリクエストを受け取り、次のページキャッシュへのアクセスを待ちます。プリフェッチャは Next-Line プリフェッチアルゴリズムを採用しており、ミスまたはヒットしたがヒットしたエントリがプリフェッチエントリである場合に、次のプリフェッチリクエストを生成します。

### L1 TLB からのリクエスト受信と応答返却

L2 TLB は全体として、L1 TLB からの PTW リクエストを受け取ります。L1 TLB から送信された PTW リクエストは、2レベルのリピータを介して L2 TLB に渡されます。L2 TLB は、リクエストが itlbRepeater または dtlbRepeater のどちらから来たかに応じて、それぞれ itlbRepeater または dtlbRepeater に応答を返します。L2 TLB は L1 TLB から送信された仮想ページ番号を受け取り、L1 TLB には第1段階のページテーブル、第2段階のページテーブルなどの情報を返します。L2 TLB の動作は L1 TLB に対して透過的であり、L1 TLB と L2 TLB は一部の信号インターフェースを介してのみ対話する必要があります。

### L2 Cache への PTW リクエスト送信

L2 TLB は TileLink バスを介して L2 Cache に PTW リクエストを送信し、L2 Cache とは ptw_to_l2_buffer を介して接続され、ptw_to_l2_buffer に TileLink A チャネルと D チャネル関連の信号を提供および受信します。

### 信号とレジスタの複製

L2 TLB モジュールは大きいため、sfence 信号や csr レジスタなどが多くの部分を駆動する必要があります。そのため、sfence 信号や csr レジスタを複数コピーする必要があります。レジスタを複製すると、タイミングの最適化と物理実装が容易になりますが、機能実装とは無関係で、複製された内容は完全に同じです。複製された信号とレジスタを使用して、異なる場所のコンポーネントを駆動できます。

### 例外処理メカニズム

L2 TLB で発生する可能性のある例外には、ゲストページフォールト、ページフォールト、アクセスフォールト、ECC チェックエラーなどがあります。ゲストページフォールト、ページフォールト、アクセスフォールトは L1 TLB に渡され、L1 TLB はリクエストのソースに応じて処理を渡します。ECC チェックエラーは L2 TLB 内部で処理され、現在のエントリを無効にし、ミスの結果を返して再度ページウォークを実行します。このドキュメントの第6部「例外処理メカニズム」を参照してください。

### TLB 圧縮

仮想化拡張機能を追加した後、L2TLB の stage1 は TLB 圧縮のロジック設計を再利用し、L1TLB に返される構造も TLB 圧縮の構造ですが、L1TLB では TLB 圧縮は有効になっていません。一方、stage2 は TLB 圧縮構造を採用せず、resp 時に単一のページテーブルのみを返します。

L2 TLB はメモリにアクセスするたびに 512 ビットの幅で、一度に8つのページテーブルエントリを返すことができます。ページキャッシュの l3 エントリは SRAM で構成されており、リフィル時に連続する8つのページテーブルエントリを保存できます。ページキャッシュの sp エントリはレジスタファイルで構成されており、リフィル時に単一のページテーブルエントリのみを保存します。したがって、ページキャッシュがヒットして L1 TLB に返すとき（2段階アドレス変換でない場合。2段階アドレス変換の場合、第1段階がヒットすると PTW に送信されて後続の処理が行われます）、ヒットしたのが 4KB ページテーブルであれば、ページキャッシュに保存されている連続する8つのページテーブルエントリを圧縮できます。ヒットしたのが大ページであれば、圧縮せずに直接 L1 TLB にリフィルします。（実際には、1GB または 2MB の大ページの欠落はまれであるため、4KB ページのみの圧縮を考慮します。4KB ページの ppn は24ビットであり、連続する8エントリを圧縮した後、これらのページテーブルの上位21ビットの ppn が同じである必要があります。1GB または 2MB の大ページの場合、ppn の下位9ビットは物理アドレスの生成には使用されないため、現在の設計では無意味です）

ページキャッシュがミスし、ページテーブルウォーカーまたは最終レベルページテーブルウォーカーを介してメモリ内のページテーブルにアクセスした後、メモリ内のページテーブルは L1 TLB に返され、同時にページキャッシュにリフィルされます。第2段階のアドレス変換が必要な場合、ハイパーバイザページテーブルウォーカーでアクセスされたページテーブルもページキャッシュにリフィルされ、HPTW は最終的な変換結果を PTW または LLPTW に返します。PTW または LLPTW は、2段階のページテーブルをすべて L1TLB に返します。2段階でない変換リクエストが L1 TLB に返されるときも、連続する8つのページテーブルエントリを圧縮できます。ページテーブルウォーカーはリーフノードにアクセスした場合にのみ直接 L1 TLB に返すため、ページテーブルウォーカーが L1 TLB に返すページテーブルはすべて大ページです。大ページはパフォーマンスへの影響が小さいため、最適化手法の実装の単純さと、ページキャッシュの sp エントリのデータパスを再利用することを考慮して、ページテーブルウォーカーが返す大ページは圧縮されません。

L2 TLB は 4KB ページテーブルのみを圧縮します。RISC-V 特権レベルマニュアルの Sv39 ページングメカニズムによると、4KB ページテーブルが存在する物理アドレスの下位3ビットは、仮想ページ番号の下位3ビットと同じです。したがって、ページキャッシュまたは最終レベルページテーブルウォーカーが返す連続する8つのページテーブルエントリは、仮想ページ番号の下位3ビットでインデックス付けできます。ここで、valid ビットは圧縮後のページテーブルエントリが有効かどうかを示します。L1 TLB が送信したページテーブル検索リクエストの仮想ページ番号の下位3ビットに基づいて、対応するページテーブルエントリにインデックスを付けます。このページテーブルエントリの valid は必ず1になります。このページテーブルエントリと連続する他の7つのページテーブルエントリについては、それらの物理ページ番号の上位ビットとページテーブル属性ビットが同じかどうかを比較します。物理ページ番号の上位ビットとページテーブル属性ビットが、仮想ページ番号の下位3ビットでインデックス付けされたページテーブルエントリと等しい場合、valid ビットは1になり、そうでない場合は0になります。同時に、L2 TLB は pteidx も返します。これは、これら8つの連続するページテーブルエントリのうち、どれが L1 TLB が送信した vpn に対応するページテーブルであるかを示します。L2 TLB の圧縮を [@fig:L2TLB-compress-1;@fig:L2TLB-compress-2] に示します。

TLB 圧縮を実装した後、L1 TLB の各エントリは圧縮された TLB エントリになり、仮想ページ番号の上位ビットで検索されます。TLB エントリがヒットする条件は、仮想ページ番号の上位ビットが同じであることに加えて、仮想ページ番号の下位ビットに対応する valid ビットが1である必要があります。これは、検索されたページテーブルエントリが圧縮後の TLB エントリで有効であることを示します。TLB 圧縮と L1 TLB に関連する部分の詳細については、L1TLB モジュールの紹介を参照してください。

L1 TLB からのリクエストは、まずページキャッシュにアクセスします。2段階アドレス変換ではないリクエストの場合、リーフノードにヒットすると直接 L1 TLB に返されます。そうでない場合は、ページキャッシュでヒットしたページテーブルのレベルと、ページテーブルウォーカーおよび最終レベルページテーブルウォーカーの空き状況に応じて、ページテーブルウォーカー、最終レベルページテーブルウォーカー、またはミスキューに入ります（セクション 5.3.7 参照）。一方、2段階アドレス変換リクエストの場合、リクエストが onlyStage1 であれば、非2段階アドレス変換リクエストと同様に処理されます。リクエストが onlyStage2 で、リーフページテーブルにヒットした場合は直接返され、ヒットしなかった場合はページテーブルウォーカーに送信されて変換されます。リクエストが allStage の場合、ページキャッシュは一度に1つのページテーブルしかクエリできないため、まず第1段階のページテーブルをクエリします。2つのケースがあります。第1段階のページテーブルがヒットした場合、ページテーブルウォーカーに送信され、その後の変換プロセスが実行されます。第1段階のページテーブルがリーフノードにヒットしなかった場合、ヒットしたページテーブルのレベルと、ページテーブルウォーカーおよび最終レベルページテーブルウォーカーの空き状況に応じて、ページテーブルウォーカー、最終レベルページテーブルウォーカー、またはミスキューに入ります。ページテーブルへのアクセスを高速化するために、ページキャッシュは3レベルのページテーブルをすべて個別にキャッシュしており、同時に3レベルのページテーブルをクエリできます（セクション 5.3.7 参照）。ページキャッシュは ECC チェックをサポートしており、ECC チェックでエラーが発生した場合は、このエントリをフラッシュして再度ページウォークを実行します。

ページテーブルウォーカーは、ページキャッシュからのリクエストを受け取り、ハードウェアページテーブルウォークを実行します。2段階アドレス変換ではないリクエストの場合、ページテーブルウォーカーは最初の2レベル（1GB および 2MB）のページテーブルのみにアクセスし、4KB ページテーブルにはアクセスしません。4KB ページテーブルへのアクセスは、最終レベルページテーブルウォーカーが担当します。ページテーブルウォーカーがリーフノード（大ページ）にアクセスした場合、L1 TLB に返されます。そうでない場合は、最終レベルページテーブルウォーカーに返す必要があり、最終レベルページテーブルウォーカーが最終レベルのページテーブルにアクセスします。ページテーブルウォーカーは同時に1つのリクエストしか処理できず、最初の2レベルのページテーブルを並行してアクセスすることはできません。2段階アドレス変換リクエストの場合、最初のケースとして、allStage リクエストで第1段階の変換ページテーブルがヒットした場合、PTW は第2段階のリクエストをページキャッシュに送信してクエリします。ヒットしなかった場合、ハイパーバイザページテーブルウォーカーに送信され、第2段階の変換結果が PTW に返されます。2番目のケースとして、allStage リクエストで第1段階の変換リーフノードがヒットしなかった場合、PTW の変換プロセスは非仮想化リクエストの変換と似ていますが、PTW の変換プロセスで出現する物理アドレスがゲスト物理アドレスである点が異なります。これは、メモリにアクセスする前に第2段階のアドレス変換を行う必要があります。詳細については、ページテーブルウォーカーのモジュール紹介を参照してください。3番目のケースとして、onlyStage2 リクエストの場合、PTW は外部に第2段階の変換リクエストを送信し、resp を受信した後、L1TLB に返します。4番目のリクエストは onlyStage1 リクエストであり、このリクエストの PTW 内部での処理プロセスは非仮想化リクエストの処理プロセスと一致します。

ミスキューは、ページキャッシュと最終レベルページテーブルウォーカーからのリクエストを受け取り、次のページキャッシュへのアクセスを待ちます。プリフェッチャは Next-Line プリフェッチアルゴリズムを採用しており、ミスまたはヒットしたがヒットしたエントリがプリフェッチエントリである場合に、次のプリフェッチリクエストを生成します。

* arb1: 2 to 1 のアービタ、図中の Arbiter 2 to 1。入力は ITLB (itlbRepeater2) と DTLB (dtlbRepeater2)。出力は Arbiter 5 to 1 へ。
* arb2: 5 to 1 のアービタ、図中の Arbiter 5 to 1。入力はミスキュー、ページテーブルウォーカー、arb1、hptw_req_arb、プリフェッチャ。出力はページキャッシュへ。
* hptw_req_arb: 2 to 1 のアービタ。入力はページテーブルウォーカーと最終レベルページテーブルウォーカー。出力はページキャッシュへ。
* hptw_resp_arb: 2 to 1 のアービタ。入力はページキャッシュとハイパーバイザページテーブルウォーカー。出力は PTW または LLPTW へ。
* outArb: 1 to 1 のアービタ。入力は mergeArb。出力は L1TLB の resp へ。
* mergeArb: 3 to 1 のアービタ。入力はページキャッシュ、ページテーブルウォーカー、最終レベルページテーブルウォーカー。出力は outArb へ。
* mq_arb: 2 to 1 のアービタ。入力はページキャッシュと最終レベルページテーブルウォーカー。出力はミスキューへ。
* mem_arb: 3 to 1 のアービタ。入力はページテーブルウォーカー、最終レベルページテーブルウォーカー、最終レベルページテーブルウォーカー。出力は L2 Cache へ。（最終レベルページテーブルウォーカー内部にも mem_arb があり、すべての最終レベルページテーブルウォーカーから L2 Cache への PTW エントリを仲裁し、その後この mem_arb に渡されます）

![L2 TLB モジュールヒットパス](../../figure/image36.jpeg){#fig:L2TLB-hit-passthrough}

L2 TLB モジュールのヒットパスを [@fig:L2TLB-hit-passthrough] に示します。ITLB と DTLB からのリクエストは、まず仲裁を通過し、その後ページキャッシュに送られて検索されます。2段階アドレス変換ではないリクエスト、第2段階の変換のみのリクエスト、または第1段階の変換のみのリクエストの場合、ページキャッシュがヒットすると、ページキャッシュでヒットしたページテーブルエントリと物理アドレスなどの情報が直接 L1 TLB に返されます。allStage の場合、ページキャッシュはまず第1段階のページテーブルを検索し、第1段階がヒットすると PTW に送信されます。PTW は hptw リクエストを送信し、hptw リクエストはページキャッシュに入って検索されます。ヒットした場合は PTW に送信され、ヒットしなかった場合は HPTW に送信されます。HPTW は検索終了後、結果を PTW に送信します。HPTW がメモリから取得したページテーブルもページキャッシュにリフィルされます。ITLB と DTLB が送信するすべての PTW リクエスト、および PTW または LLPTW が送信する hptw リクエストは、必ず最初にページキャッシュの検索を行います。

一方、ミスの場合、すべてのモジュールが関与する可能性があります。ITLB と DTLB からのリクエストは、まず仲裁を通過し、その後ページキャッシュに送られて検索されます。ページキャッシュがミスした場合、状況に応じてミスキューに入る可能性があります（PTW または LLPTW がページキャッシュに送信した hptw リクエストまたはプリフェッチリクエストの場合は、ミスキューには入りません）。ミスしたリクエストがミスキューに入るのは、バイパスリクエストが発生した場合、L1TLB がページキャッシュに送信し（isFirst）、PTW に入る必要があるリクエスト、ミスキューが PTW に送信し、PTW がビジーなリクエスト、LLPTW に送信し、LLPTW がビジーなリクエストです。ページキャッシュは、ページキャッシュでヒットしたページテーブルのレベルに応じて、ページテーブルウォーカーまたは最終レベルページテーブルウォーカーに入って検索するかを決定する必要があります（hptw リクエストの場合は、HPTW に送信されます）。ページテーブルウォーカーは同時に1つのリクエストしか処理できず、メモリ内の最初の2レベルのページテーブルの内容にアクセスできます。最終レベルページテーブルウォーカーは、最後のレベルの 4KB ページテーブルへのアクセスを担当します。ハイパーバイザページテーブルウォーカーは、同時に1つのリクエストしか処理できません。

ページテーブルウォーカー、最終レベルページテーブルウォーカー、およびハイパーバイザページテーブルウォーカーはすべて、メモリにリクエストを送信して、メモリ内のページテーブルの内容にアクセスできます。物理アドレスを介してメモリ内のページテーブルの内容にアクセスする前に、PMP および PMA モジュールを介して物理アドレスをチェックする必要があります。PMP および PMA のチェックが失敗した場合、メモリにリクエストは送信されません。ページテーブルウォーカー、最終レベルページテーブルウォーカー、およびハイパーバイザページテーブルウォーカーからのリクエストは、仲裁を経た後、TileLink バスを介して L2 Cache にリクエストを送信します。

ページテーブルウォーカーと最終レベルページテーブルウォーカーはどちらも、L1 TLB に PTW 応答を返す可能性があります。ページテーブルウォーカーは、以下のようないくつかの状況で応答を生成する可能性があります。

* 2段階でない変換リクエストと第1段階の変換のみのリクエストで、リーフノード（1GB または 2MB の大ページ）にアクセスした場合、直接 L1 TLB に返します。
* 第2段階の変換のみのリクエストで、第2段階の変換結果を受け取った後。
* 2段階の変換が両方あるリクエストで、第1段階のリーフページテーブルと第2段階のリーフページテーブルの両方が得られた後。
* 第2段階の変換で返された結果にページフォールトまたはアクセスフォールトが発生した場合。
* PMP または PMA のチェックでページフォールトまたはアクセスフォールトが発生した場合も、同様に L1 TLB に返す必要があります。

最終レベルページテーブルウォーカーは、必ず L1 TLB に応答を返します。これには、以下のようないくつかの可能性があります。

* 2段階でない変換リクエストと第1段階の変換のみのリクエストで、リーフノード（4KB ページ）にアクセスした場合。
* 2段階の変換が両方あるリクエストで、第1段階のリーフページテーブルと第2段階のリーフページテーブルの両方が得られた後。
* PMP または PMA のチェックでアクセスフォールトが発生した場合。

## インターフェースタイミング

### L2 TLB とリピータのインターフェースタイミング

L2 TLB とリピータのインターフェースタイミングを [@fig:L2TLB-repeater-time] に示します。L2 TLB とリピータは valid-ready 信号でハンドシェイクを行います。リピータは L1 TLB が発行した PTW リクエストとリクエストの仮想アドレスを L2 TLB に送信します。L2 TLB は結果を検索した後、物理アドレスと対応するページテーブルをリピータに返します。

![L2TLB とリピータのインターフェースタイミング](../../figure/image38.svg){#fig:L2TLB-repeater-time}

### L2 TLB と L2 Cache のインターフェースタイミング

L2 TLB と L2 Cache のインターフェースタイミングは、TileLink バスプロトコルに従います。
