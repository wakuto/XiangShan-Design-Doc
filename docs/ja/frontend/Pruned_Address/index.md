# 昆明湖 PrunedAddr ドキュメント

## 背景

RISC-Vマニュアルでは、BタイプおよびJタイプの命令について次のように記述されています。

> SフォーマットとBフォーマットの唯一の違いは、12ビットの即値フィールドがBフォーマットでは2の倍数の分岐オフセットをエンコードするために使用されることです。従来のように命令エンコードされた即値のすべてのビットをハードウェアで1ビット左にシフトする代わりに、中央のビット（imm[10:1]）と符号ビットは固定位置に留まり、Sフォーマットの最下位ビット（inst[7]）がBフォーマットの高位ビットをエンコードします。
>
> 同様に、UフォーマットとJフォーマットの唯一の違いは、20ビットの即値がU即値を形成するために12ビット左にシフトされ、J即値を形成するために1ビット左にシフトされることです。UおよびJフォーマットの即値における命令ビットの位置は、他のフォーマットおよび互いのオーバーラップを最大化するように選択されています。

これは、`jalr`を除くすべての分岐命令について、ジャンプ先の最下位ビットが必ず0であることを意味します。`jalr`命令については、マニュアルでジャンプ先の計算について次のように記述されています。

> ターゲットアドレスは、符号拡張された12ビットのI即値をレジスタrs1に加算し、結果の最下位ビットをゼロに設定することによって取得されます。

これは、`jalr`のジャンプ先の最下位ビットも0であることを意味します。

これら2つの部分を総合すると、すべてのPCの最下位ビットは必ず0であることがわかります。したがって、フロントエンドのPCに関連するすべての部分で最下位ビットを保存する必要がなくなり、面積を節約できます。

実際には、C拡張がオフの場合、PCの下位2ビットは必ず0であり、そうでなければ命令の非整列例外が報告されます。

## 使用ガイド

`PrunedAddr`の設計目標は、`UInt`と可能な限り同じように使用できるようにすることです。ただし、Chiselの制限により、この目標を完全に達成することはできません。`UInt`と異なる点については、`Reg`や`Wire`に類似していると考えることができます。具体的な使用ガイドは次のとおりです。

- `UInt`から`PrunedAddr`への変換には`PrunedAddrInit`を使用します。例：`val addr1 = PrunedAddrInit(addr2)`、ここで`addr2`の型は`UInt`です。
- `PrunedAddr`から`UInt`への変換には`toUInt`を使用します。例：`addr.toUInt`
- `def +(offset: UInt)`というメソッドは、`offset`が即値の場合にのみ使用してください。その他の場合は、`def +(offset: PrunedAddr)`を使用する必要があります。`offset`が`UInt`で即値でない場合は、`offset`を`PrunedAddr`に変換する必要があります。

## 未解決の問題

- 現在、`PrunedAddr`の使用はフロントエンド内部に限定されており、フロントエンドからバックエンドへのインターフェースでは依然として`UInt`が使用されています。理想的には、バックエンドもすべて`PrunedAddr`を使用すべきです。その場合、`toUInt`メソッドはデバッグ情報の出力時にのみ使用されるべきです。
- `def >>(offset: Int)`というメソッドは、混乱を減らすために削除すべきです。対応する機能は、対応するビットを直接選択することで実現できます。
- 切り詰めるビット数については、現在の実装では`instOffset`というパラメータが使用されています。理論的には、このパラメータはC拡張のオン/オフに応じて変化するはずです。しかし、現在XiangShanはC拡張をオフにすることをサポートしておらず、C拡張をオフにした場合の正当性はまだ検証されていません。
